# รายงาน 3 ระดับ — แคตาล็อกรายงาน NetSuite (Matrix แผนก × ระดับ)

**วันที่:** 2026-08-04
**ขอบเขต:** เพิ่ม sub-view ที่ 4 ใต้แท็บ *โปรเจค* ใน `index.html`
**ต้นทางข้อมูล:** `NetSuite_รายงาน 3 ระดับ.xlsx` (ชีต "รายงาน 3 ระดับ", 90 รายการ, 10 คอลัมน์)

## เป้าหมาย

ยกรายการ "รายงานที่ต้องการ แบ่ง 3 ระดับ (ทุกแผนก)" จาก Excel เข้ามาเป็นแคตาล็อกในแอป ให้ทีมค้นหา/ดูได้ที่เดียวกับข้อมูลอื่น และกดเข้าตอนพรีเซ้น CEO ได้ทันที โดยแก้ไขได้แบบ realtime เพื่อทยอยเติมแหล่งข้อมูลและไฟล์ตัวอย่างที่ยังขาด

**นิยามระดับ (จากไฟล์ต้นทาง):** Operational = หน้างานรายวัน · Managerial = หัวหน้า/PM รายสัปดาห์-เดือน · Executive = ผู้บริหาร รายเดือน-ไตรมาส

## สิ่งที่ผู้ใช้ได้

1. **Matrix แผนก × ระดับ** — เห็นภาพรวมทั้ง 90 รายงานในหน้าเดียว ตัวเลขคลิกเพื่อกรองได้
2. **ตารางแคตาล็อก** — ค้นหา/กรอง แล้วคลิกดูรายละเอียดเต็ม
3. **Drawer แก้ไข** — เติมข้อมูลที่ยังขาด บันทึกลง Firestore ทันที ทุกคนเห็นพร้อมกัน

## 1. Data model

Firestore collection ใหม่ `report_levels` — per-item document, doc id = `String(_id)`, realtime ผ่าน `window.DB` เหมือน collection อื่น

| field | คอลัมน์ต้นทาง | ชนิด | กรอกมาแล้ว |
|---|---|---|---|
| `_id` | (ลำดับแถวในชีต 1–90) | number | 90/90 |
| `dept` | แผนก | string | 90/90 |
| `level` | ระดับ | string | 90/90 |
| `name` | ชื่อรายงาน | string | 90/90 |
| `user` | ผู้ใช้หลัก | string | 90/90 |
| `freq` | ความถี่ | string | 90/90 |
| `kpi` | ตัวชี้วัด / ข้อมูลหลัก | string | 89/90 |
| `src` | แหล่งข้อมูล (NetSuite) | string | 32/90 |
| `decide` | ใช้ตัดสินใจอะไร | string | 69/90 |
| `sample` | ชื่อไฟล์ตัวอย่าง | string | 16/90 |
| `want` | กรณีไม่มีไฟล์ตัวอย่าง อยากเห็นข้อมูลอะไรบ้าง | string | 9/90 |

**การเตรียม seed:**
- อ่านจาก `.xlsx` ด้วย parser ที่รองรับ **เซลล์ว่างแบบ self-closing** (`<c r="G12" s="11"/>`) — ถ้าไม่รองรับ ค่าจะเลื่อนคอลัมน์และอ่าน shared-string index ออกมาเป็นตัวเลขแทนข้อความ
- `dept` ในไฟล์มีช่องว่างซ้อน (`"HR  บุคคล/แรงงาน"`) → normalize ด้วย `replace(/\s+/g,' ').trim()` ตอน seed เพื่อให้จัดกลุ่มได้ถูก
- ช่องที่ว่างในไฟล์เก็บเป็น `''` ไม่ใช่ `null`
- บันทึกเป็น `seed/report_levels.json` + ฝังเป็น `RPT_SEED` const ใน `index.html` (แพทเทิร์นเดียวกับ `ACT_SEED`)

## 2. Matrix แผนก × ระดับ

ตาราง 9 แถว (แผนก) × 3 คอลัมน์ (ระดับ) + คอลัมน์ **รวม**

| แผนก | Operational | Managerial | Executive | รวม |
|---|---|---|---|---|
| HR บุคคล/แรงงาน | 2 | 1 | 1 | 4 |
| FI บัญชี | 2 | 6 | 3 | 10 |
| FI บัญชี/การเงิน | 3 | 0 | 0 | 3 |
| FI การเงิน | 4 | 3 | 3 | 8 |
| MM จัดซื้อ/จ้าง | 12 | 5 | 1 | 18 |
| PM เครื่องจักร | 10 | 9 | 6 | 25 |
| SD ขาย/รายได้ | 3 | 0 | 0 | 3 |
| PS โครงการ | 1 | 11 | 2 | 14 |
| การผลิต (Manufacturing) | 2 | 2 | 1 | 5 |
| **รวม** | **39** | **37** | **17** | **90** |

### การนับเมื่อรายการครอบคลุมหลายระดับ

มี 2 รายการที่ระบุมากกว่า 1 ระดับ:

| # | แผนก | ชื่อรายงาน | ระดับที่ระบุ |
|---|---|---|---|
| 14 | FI บัญชี | งบการเงินก่อนจัดประเภทรายการ | Managerial / Executive |
| 18 | FI การเงิน | รายงานวงเงินสินเชื่อ AVAL & PN | Operational / Managerial / Executive |

**กติกาการนับ (ตัดสินใจแล้ว):**
- **เซลล์ระดับ นับซ้ำ** — รายการหนึ่งปรากฏในทุกระดับที่ครอบคลุม เพื่อให้ตอบคำถาม "ระดับนี้มีกี่รายงาน" ได้ถูก → ผลรวมแถวล่าง 39 + 37 + 17 = 93
- **คอลัมน์ "รวม" รายแผนก นับไม่ซ้ำ** (นับเป็นรายการ) → รวมทั้งหมด = **90** ตรงกับจำนวนรายงานจริง
- ใต้ตารางมีเชิงอรรถ: *"2 รายการครอบคลุมหลายระดับ จึงถูกนับซ้ำในคอลัมน์ระดับ (รวมคอลัมน์ระดับ = 93 · รายงานทั้งหมด = 90)"*

การแยกระดับใช้การตรวจ substring บนฟิลด์ `level` — ถ้าข้อความมีคำว่า `Operational` / `Managerial` / `Executive` ก็ถือว่าอยู่ระดับนั้น (รองรับทั้ง `"Managerial / Executive"` และรูปแบบขึ้นบรรทัดใหม่)

### การคลิก

| คลิกที่ | ผลลัพธ์ |
|---|---|
| ตัวเลขในเซลล์ | กรองตารางข้างล่างเป็น แผนกนั้น × ระดับนั้น |
| ชื่อแผนก (หัวแถว) | กรองทั้งแผนก (ล้างตัวกรองระดับ) |
| ชื่อระดับ (หัวคอลัมน์) | กรองทั้งระดับ (ล้างตัวกรองแผนก) |
| ตัวเลขในคอลัมน์ "รวม" | กรองทั้งแผนก (เท่ากับคลิกหัวแถว) |
| คำว่า "รวม" มุมล่างขวา (90) | ล้างตัวกรองทั้งหมด |

เซลล์ที่ถูกเลือกอยู่ไฮไลต์ด้วยสี accent · เซลล์ค่า 0 แสดงจาง ๆ และคลิกไม่ได้

## 3. ตารางแคตาล็อก (ใต้ matrix)

| # | หัวคอลัมน์ | field | เรียงได้ |
|---|---|---|---|
| 1 | No | `_id` | ✓ |
| 2 | แผนก | `dept` (chip) | ✓ |
| 3 | ระดับ | `level` (chip) | ✓ |
| 4 | ชื่อรายงาน | `name` | ✓ |
| 5 | ผู้ใช้หลัก | `user` | — |
| 6 | ความถี่ | `freq` | ✓ |
| 7 | แหล่งข้อมูล | `src` (ว่าง = ขีด `—` สีจาง) | — |

คลิกแถว → เปิด drawer · แถวที่ยังไม่มี `src` ไม่ต้องไฮไลต์พิเศษ (เรื่อง gap ไม่ใช่เรื่องที่เมนูนี้เล่า)

**สีของ chip ระดับ:** `Operational` `#0071e3` · `Managerial` `#ff9500` · `Executive` `#5e5ce6`
รายการที่ระบุหลายระดับใช้สีของระดับสูงสุด โดยลำดับคือ `Executive` > `Managerial` > `Operational` (เช่น `"Managerial / Executive"` → สี Executive) ข้อความใน chip แสดงตามที่กรอกมาเต็ม ๆ

**สีของ chip แผนก:** ตาม prefix โมดูล — `HR` `#28cd41` · `FI` `#0071e3` · `MM` `#ff9500` · `PM` `#af52de` · `SD` `#ff3b30` · `PS` `#5e5ce6` · อื่น ๆ `#8e8e93`

## 4. แถบ filter

```
แผนก · ระดับ · ความถี่ · [ค้นหา…] · [ล้าง]
```

- `แผนก` / `ระดับ` — multi-select แบบเดียวกับหน้าอื่น (`data-multi="1"`)
- `ค้นหา` — ครอบ `name` + `user` + `kpi` + `src` + `decide` + `sample` + `want`
- `ล้าง` — ล้างทุกตัวกรองรวมถึงการเลือกในเซลล์ matrix

### ความถี่ — ยุบเหลือ 4 กลุ่มเฉพาะใน dropdown

ไฟล์ต้นทางมีข้อความความถี่ 9 แบบที่ซ้ำความหมายกัน:

| ข้อความในไฟล์ | จำนวน |
|---|---|
| รายเดือน | 35 |
| รายวัน | 21 |
| ทุกเดือน | 11 |
| รายไตรมาส | 6 |
| ทุกวัน | 5 |
| รายสัปดาห์-เดือน | 4 |
| รายวัน-สัปดาห์ | 4 |
| รายสัปดาห์ | 3 |
| สัปดาห์ | 1 |

**กติกา (ตัดสินใจแล้ว):** dropdown มี 4 ตัวเลือก — `รายวัน` · `รายสัปดาห์` · `รายเดือน` · `รายไตรมาส` — จับคู่ด้วย substring บนข้อความเดิม:

| ตัวเลือก | เข้าเงื่อนไขเมื่อ `freq` มีคำว่า | ครอบคลุม |
|---|---|---|
| รายวัน | `วัน` | 30 รายการ |
| รายสัปดาห์ | `สัปดาห์` | 12 รายการ |
| รายเดือน | `เดือน` | 50 รายการ |
| รายไตรมาส | `ไตรมาส` | 6 รายการ |

รายการที่เขียนคร่อม เช่น `รายสัปดาห์-เดือน` จะโผล่ในทั้ง 2 กลุ่ม — ตั้งใจ เพราะเป็นพฤติกรรมที่ผู้ใช้คาดหวังเวลากรอง

**ตารางและ drawer แสดงข้อความเดิมตามที่กรอกมาเสมอ — ไม่แก้ข้อมูลต้นทาง**

## 5. Drawer

เปิดจากการคลิกแถว ใช้ `#modal` + `closeModal()` เดิม แก้ไขได้ทุกฟิลด์ ปุ่ม `บันทึก / ยกเลิก / ลบ` แบบเดียวกับ Action Items

```
หัว:  รายงาน #<id> · <แผนก>
รอง:  <ระดับ> · <ความถี่>

ซ้าย:   แผนก · ระดับ · ผู้ใช้หลัก · ความถี่
        แหล่งข้อมูล (NetSuite)
        ตัวชี้วัด / ข้อมูลหลัก      (textarea)
        ใช้ตัดสินใจอะไร            (textarea)

ขวา:    ชื่อรายงาน                 (textarea)
        ชื่อไฟล์ตัวอย่าง
        กรณีไม่มีไฟล์ตัวอย่าง อยากเห็นข้อมูลอะไรบ้าง  (textarea)
```

`แผนก` และ `ระดับ` เป็น `<select>` ที่เติมตัวเลือกจากค่าที่มีอยู่จริงในข้อมูล เพื่อไม่ให้พิมพ์ผิดจนหลุดกลุ่มใน matrix — ตัวเลือกของ `ระดับ` จึงมี 5 ค่า คือ 3 ระดับเดี่ยว บวกค่ารวมอีก 2 แบบที่มีอยู่จริง (`Managerial / Executive` และ `Operational / Managerial / Executive`) ไม่ตัดทิ้ง

ปุ่ม **+ เพิ่มรายงาน** อยู่มุมขวาของแถบ filter · `_id` ใหม่ = max + 1

## 6. การวางในแอป

เพิ่มปุ่มที่ 4 ใน `#projToggle` (ปัจจุบันมี `impl` / `reqs` / `action`):

```html
<button class="pjt" data-pv="report" onclick="setProjView('report')">[icon] รายงาน 3 ระดับ</button>
```

- `setProjView()` เพิ่ม branch `report` → แสดง `#reportView` ซ่อน panel อื่น เรียก `renderRpts()`
- boot: `await loadRpts(); fillRptFilters(); rptBind();` และ `subscribeRpts();` ต่อท้ายบรรทัด subscribe เดิม

> **ข้อควรระวัง:** `#projToggle` อยู่ใน topbar และป้ายปุ่มปัจจุบันยาว (`แผนงาน (Implementation)`, `ความต้องการ (Requirements)`) การเพิ่มปุ่มที่ 4 อาจทำให้ topbar ล้นในจอแคบ → ใช้ป้ายสั้น **"รายงาน 3 ระดับ"** และตรวจ layout ที่ความกว้าง 1280px ตอน verify ถ้าล้นให้ย่อป้ายปุ่มอื่นเป็นข้อความสั้นแทน (เป็นการแก้ที่ยอมรับได้ เพราะเกิดจากงานนี้โดยตรง)
