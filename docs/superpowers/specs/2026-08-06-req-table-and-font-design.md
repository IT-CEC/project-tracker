# ตาราง Requirements: ตัดคอลัมน์รายละเอียด + แก้ฟอนต์ที่โหลดไม่ได้

**วันที่:** 2026-08-06
**ขอบเขต:** `index.html` — ตาราง Requirements + font stack ของทั้งแอป

## สิ่งที่ผู้ใช้ขอ

1. ไม่ต้องแสดงคอลัมน์ **รายละเอียด** ในตาราง เพราะต้องกดเข้าไปดูรายละเอียดแต่ละรายการอยู่แล้ว
2. ตัวหนังสือในตารางแสดงเป็น**น้ำหนักเท่ากัน**

## ต้นตอที่พบระหว่างสำรวจ — ฟอนต์ 404

ผู้ใช้เห็นคอลัมน์ PROCESS หนาไม่เท่ากันแต่ละแถว แต่การวัดพบว่า **ทุกเซลล์ตั้ง `font-weight:600` เท่ากันหมด** ปัญหาจึงไม่ได้อยู่ที่ CSS

ค้นต่อพบว่า `SF Pro Display` ที่อยู่หัวแถวของ font stack **โหลดไม่สำเร็จทั้ง 3 ไฟล์** — `@font-face` ทุกตัวขึ้นสถานะ `error` และไฟล์ตอบ **404 บนเว็บจริง** เพราะโฟลเดอร์ `sf-pro-display/` ไม่เคยถูก commit เข้า repo

ผลที่ตามมาคือทั้งแอปวาดด้วยฟอนต์สองตัวปนกัน

| ตัวอักษร | ฟอนต์ที่ได้จริง | น้ำหนัก 600 |
|---|---|---|
| ไทย | `Noto Sans Thai` (Google Fonts โหลดสำเร็จ) | มี SemiBold จริง |
| อังกฤษ | ตกไปที่ `sans-serif` ของระบบ | **ไม่มี 600 ถูกดันขึ้นเป็น 700** |

พิสูจน์ด้วยการวัดความกว้าง: `budget cost center` กว้าง **111.8px เท่ากันเป๊ะทั้งที่ 600 และ 700** แปลว่าถูก snap ขึ้น ส่วน `สร้างรหัสบัญชี` ได้ 76.92 กับ 78.49 ซึ่งต่างกัน แปลว่ามี 600 จริง

ข้อความที่ปนสองภาษาจึงหนาไม่เท่ากัน — และเกิดกับ**ทุกหน้าในแอป** ไม่ใช่แค่ตารางนี้

## สิ่งที่ทำ

### 1 · ถอด SF Pro Display ออกจาก font stack

ผู้ใช้เลือกวิธีนี้ ทั้งแอปใช้ `Noto Sans Thai` ซึ่งมีน้ำหนัก 400/500/600/700 จริงและครอบคลุมทั้งอักษรไทยและอังกฤษ

แก้ 12 จุด: `@font-face` 3 · ตัวแปร CSS 4 (`--font-ui` `--font-sans` `--font-mono` `--serif`) · `font-family` 2 · `font` shorthand 1 · `ctx.font` ใน canvas 2

canvas เดิมเขียน `"SF Pro Display",sans-serif` โดย**ไม่มีฟอนต์ไทยสำรองเลย** เปลี่ยนเป็น `"Noto Sans Thai",sans-serif` ให้ตรงกับส่วนอื่น

**ผลข้างเคียงที่ตั้งใจ: ตัวอักษรอังกฤษทั้งแอปเปลี่ยนหน้าตา** จากฟอนต์ระบบเป็น Noto Sans — ผู้ใช้รับทราบและเลือกทางนี้เอง

### 2 · ลบคอลัมน์รายละเอียด

ตัด `<col style="width:280px">` · `<th>` · `<td>` ออก เหลือ 8 คอลัมน์ (นับคอลัมน์ปุ่ม) ความกว้าง 280px ที่คืนมาเฉลี่ยให้คอลัมน์ที่เหลือ

ข้อมูลไม่ได้หายไปไหน — ยังเปิดดูได้จากหน้าต่างรายละเอียดเหมือนเดิม

### 3 · ย้าย Owner มาไว้หลัง Process

ลำดับใหม่: `Module · Sub-Module · Process · Owner · Request Type · Fit-Gap · Status`

ย้ายพร้อมกันทั้ง `<col>` `<th>` `<td>` และ `data-sort="owner"` ติดไปกับ `<th>` การคลิกหัวคอลัมน์เพื่อเรียงลำดับจึงยังทำงาน

ไฟล์ export ไม่กระทบ — `downloadXlsx` สร้างจาก `HEADERS` + `REQS` ตามโมเดลข้อมูล ไม่ได้อ่านจาก DOM จึงยังมีคอลัมน์ Requirement และลำดับเดิมครบ

### 4 · น้ำหนักตัวอักษรเท่ากัน

PROCESS เดิมเป็น `600` เปลี่ยนเป็นน้ำหนักเดียวกับคอลัมน์อื่น (400)

**ยังคงสีเข้ม (`--ink`) ไว้** ต่างจาก SUB-MODULE / OWNER ที่เป็นเทาอ่อน — ผู้ใช้ขอให้ *น้ำหนัก* เท่ากัน ไม่ได้ขอให้สีเท่ากัน การแยกลำดับด้วยสีจึงยังอยู่ และยังกวาดสายตาหาแถวได้

chip ของ MODULE ยังเป็น 600 เพราะเป็น badge ไม่ใช่ข้อความในตาราง และหลังแก้ฟอนต์แล้วมันเรนเดอร์สม่ำเสมอเองอยู่แล้ว

### 5 · แก้คอมเมนต์ที่ไม่จริงแล้ว

คอมเมนต์เหนือ `tabular-nums` อ้างว่า *"เลข 1 แคบกว่า 0 อยู่ 27% ใน SF Pro Display"* ซึ่งใช้ไม่ได้อีกเมื่อถอดฟอนต์นั้นออก

วัดใหม่กับฟอนต์ที่ใช้จริง: `Noto Sans Thai` ให้ `0` และ `1` กว้าง **7.436px เท่ากัน** — มีตัวเลขความกว้างเท่ากันมาให้อยู่แล้ว `tabular-nums` จึงเหลือบทบาทเป็นตัวกันเหนียวสำหรับฟอนต์สำรอง แก้คอมเมนต์ให้ตรงตามนี้

## ไม่ทำ

- ไม่เอาไฟล์ SF Pro ใส่ repo — เป็นฟอนต์ของ Apple ที่ license จำกัดการใช้บนแพลตฟอร์ม Apple การโฮสต์ให้เบราว์เซอร์ Windows โหลดอาจมีปัญหาสิทธิ์
- ไม่แตะคอลัมน์อื่น ตัวกรอง การเรียงลำดับ หรือหน้าต่างรายละเอียด

## การตรวจสอบ

1. ไม่มี `@font-face` ไหนขึ้นสถานะ `error` และไม่มีคำขอไฟล์ `.OTF` ยิงออกไปอีก
2. `600` เป็นน้ำหนักจริงทั้งไทยและอังกฤษ — วัดว่าความกว้างที่ 600 ต่างจาก 700 (เดิมเท่ากันเพราะถูกดันขึ้น)
3. ตารางเหลือ 7 คอลัมน์ข้อมูล ไม่มี "รายละเอียด" และจำนวน `<col>` เท่ากับ `<th>`
4. ทุกเซลล์ข้อความในแถวเป็นน้ำหนัก 400 เท่ากัน
5. `0` และ `1` กว้างเท่ากันในฟอนต์ที่ใช้จริง
6. ทุก panel และทุก sub-view ยัง render ได้ทั้ง light/dark · ไม่มี JS error
7. ลำดับคอลัมน์เป็น Module · Sub-Module · Process · Owner · Request Type · Fit-Gap · Status และข้อมูลในแถวตรงกับหัวทุกช่อง
8. คลิกหัว Owner แล้วตารางเรียงใหม่จริง
