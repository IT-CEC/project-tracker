# หน้าต่างรายละเอียดงาน — แก้บั๊กและจัดดีไซน์

**วันที่:** 2026-08-06
**ขอบเขต:** `index.html` — `openPI` drawer และตัวปิด modal

## บั๊ก — ลากเมาส์ออกนอกกรอบแล้วกรอบปิด

```js
document.getElementById('modal').onclick=e=>{if(e.target.id==='modal')closeModal();};
```

เหตุการณ์ `click` ยิงที่**บรรพบุรุษร่วมของจุดกดกับจุดปล่อย** เมื่อทั้งสองต่างกัน กดในช่องข้อความแล้วลากออกไปปล่อยบนพื้นหลัง ตัวร่วมคือ `#modal` เอง เงื่อนไขจึงเป็นจริงและปิดกรอบทิ้ง — เสียงานที่กำลังพิมพ์

**แก้:** จำเป้าหมายของ `mousedown` แล้วปิดเฉพาะเมื่อ**ทั้งจุดกดและจุดปล่อยอยู่บนพื้นหลัง**

การคลิกพื้นหลังตรง ๆ เพื่อปิดยังทำงานเหมือนเดิม — ทดสอบทั้งสองเส้นทาง

## ทำไมรู้สึกขัด — สาเหตุหลัก

**หน้าตาเป็นฟอร์ม แต่พฤติกรรมเป็นการแก้สด**

ทุกช่องบันทึกทันทีที่เปลี่ยนผ่าน `onchange` แต่ท้ายกรอบมีปุ่มแบบฟอร์ม ผู้ใช้จึงอ่านไม่ออกว่าปิดแล้วข้อมูลถูกเก็บหรือถูกทิ้ง

**แก้:** ใส่ข้อความ `บันทึกอัตโนมัติทุกครั้งที่แก้` พร้อมจุดเขียวที่ท้ายกรอบ บอกพฤติกรรมจริงตรง ๆ แทนที่จะให้เดา

## ปุ่มลบอยู่ตำแหน่งของปุ่มยืนยัน และผิดธรรมเนียมของแอปเอง

แอปมี `.btn-danger{margin-left:auto}` ที่ดันปุ่มอันตรายไปขวาสุด ห่างจากปุ่มปลอดภัย — หน้า Action Items และ Reports ใช้อยู่

แต่ drawer นี้ใช้ `btn-sec` ใส่สีแดง inline ปุ่มลบจึงไปอยู่**ซ้ายสุด ตำแหน่งที่ปกติเป็นปุ่มหลัก**

**แก้:** เปลี่ยนไปใช้ `btn-danger` ตามธรรมเนียมเดิม ได้ระยะห่างจากปุ่มปิดมาด้วย (วัดได้ 722px)

## ป้ายกำกับปนสองภาษา

`.fld label` ตั้ง `text-transform:uppercase` ภาษาอังกฤษจึงตะโกน `PRIORITY` `START DATE` ส่วนไทยเงียบ อยู่คอลัมน์เดียวกันโดยไม่มีแบบแผน

**แก้:** ไทยนำทั้งหมด วงเล็บอังกฤษเฉพาะศัพท์เฉพาะที่ทีมใช้ — `ความสำคัญ (Priority)` · `วันเริ่ม` · `วันสิ้นสุด` · `หมุดหมาย (Milestone)` · `ผู้รับผิดชอบ`

**จำกัดเฉพาะ drawer ของ Project Plan** — `<label>Priority</label>` มีอีกจุดใน `openAct` ซึ่งเป็นคนละหน้าที่ไม่ได้ขอ ส่วน `openAP` ใช้ไทยนำอยู่แล้ว

## บันทึกความคืบหน้า — ของใหม่

งานไม่เคยมีฟิลด์ข้อความเลยสักช่อง (Action Items มี `note`/`note2` แต่งานใน Project Plan ไม่มี)

เพิ่ม `log` เป็นอาร์เรย์ `{t, m}` ต่อท้ายพร้อมเวลา **ไม่ใช่ช่องเดียวที่เขียนทับ** เพราะการรู้ว่าอัปเดตเมื่อไรมีค่ากับการติดตามโครงการ

- แสดงใหม่สุดขึ้นบน
- ลบทีละรายการได้ (ปุ่ม × โผล่ตอน hover) พร้อมถามยืนยัน
- `piSaveTask` บันทึกทั้งอ็อบเจกต์ จึงไม่ต้องแตะชั้น persistence

วางในคอลัมน์ขวาซึ่งเดิมเกือบว่างทั้งหมด ขณะที่คอลัมน์ซ้ายอัด 9 ช่อง — แก้ความไม่สมดุลไปด้วย

## การตรวจสอบ (เบราว์เซอร์จริง)

1. กดในช่องข้อความแล้วลากออกไปปล่อยนอกกรอบ → **กรอบยังเปิดอยู่**
2. คลิกพื้นหลังตรง ๆ → ปิดได้เหมือนเดิม
3. เพิ่มบันทึก → เก็บ `{t:'03/09/2026 16:32', m:'…'}` · เขียน **1 เอกสาร** ลง `pi_tasks` · ขึ้นบนจอทันที
4. ท้ายกรอบเรียง `บันทึกอัตโนมัติ` · `ปิด` · `ลบงาน` โดยลบงานถูกดันไปขวา 722px
5. ป้ายกำกับเป็นไทยนำครบ 9 ช่อง
6. ไม่มี JS error

## เพิ่มเติม — แก้ไขบันทึกได้

**วันที่:** 2026-08-06

ผู้ใช้ถามว่าบันทึกความคืบหน้าลบหรือแก้ได้ไหม — **ลบได้อยู่แล้ว** (ปุ่ม × โผล่ตอนชี้เมาส์ พร้อมถามยืนยัน) แต่**แก้ไม่ได้** ถ้าพิมพ์ผิดต้องลบแล้วเพิ่มใหม่ ซึ่งจะได้เวลาใหม่ที่ไม่ตรงกับตอนบันทึกจริง

เสนอสองแบบ — แก้เงียบ ๆ คงเวลาเดิม หรือแก้แล้วต่อท้ายว่าถูกแก้เมื่อไร ผู้ใช้เลือกแบบแรก เพราะเป็นบันทึกภายในทีมเพื่อติดตามงาน ไม่ใช่หลักฐานที่ต้องรักษาความถูกต้องของประวัติ

### วิธี

คลิกที่ข้อความ → กลายเป็นช่องพิมพ์ เลือกข้อความไว้ให้ · คลิกออกบันทึก · Escape ยกเลิก

ตามแพทเทิร์นเดียวกับ `piRenameInline` และ `piPhDatesInline` ที่แอปใช้อยู่ ต่างตรงที่ใช้ textarea และไม่ผูก Enter กับการบันทึก เพราะบันทึกเป็นข้อความหลายบรรทัดได้ Enter จึงควรขึ้นบรรทัดใหม่ตามปกติ

**เวลาไม่เปลี่ยน** — แก้เฉพาะ `m` ไม่แตะ `t`

### จุดที่ต้องระวัง — ดัชนีของรายการ

`piLogSection` แสดงใหม่สุดขึ้นบนด้วย `.reverse()` **หลังจาก** `map` ใส่ดัชนีลงไปแล้ว ดัชนีที่ฝังใน `onclick` จึงเป็นดัชนีของอาร์เรย์จริง ไม่ใช่ตำแหน่งบนจอ

ทดสอบทั้งสองปลาย: แก้รายการบนสุดบนจอ → ไปโดน index 2 (ใหม่สุด) · แก้รายการล่างสุดบนจอ → ไปโดน index 0 (เก่าสุด) ถูกทั้งคู่

### การตรวจสอบ (เบราว์เซอร์จริง)

1. คลิกข้อความ → เป็นช่องพิมพ์ · คลิกออก → บันทึก · เขียน 1 เอกสารลง `pi_tasks`
2. **เวลาเดิมคงอยู่** (`03/09/2026 16:32` ไม่เปลี่ยน)
3. Escape → ข้อความกลับเป็นค่าเดิม ไม่บันทึก
4. ดัชนีถูกทั้งรายการบนสุดและล่างสุด
5. ลบยังทำงาน — จาก 3 รายการเหลือ 2 · ปุ่มซ่อนตอนไม่ชี้ โผล่ตอนชี้
6. ไม่มี JS error
