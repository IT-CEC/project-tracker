# แถบสรุปช่วงเวลาบนแถวหัวเฟส (Gantt)

**วันที่:** 2026-08-06
**ขอบเขต:** `index.html` — แถวหัวเฟสใน `renderPIGantt()`

## สิ่งที่ผู้ใช้ขอ

แถวหัวเฟส เช่น `02_Solution Definition (BRD)` ตอนนี้มีแต่ป้ายชื่อ ไม่มีอะไรในแถบเวลา
อยากให้มีแถบคุมภาพใหญ่เพื่อเห็นไทม์ไลน์ของเฟสนั้น

**ข้อกำหนดจากผู้ใช้: ห้ามกระทบข้อมูลจริง** เพราะมีการอัปเดต timeline จริงไว้แล้ว

## ไม่มีการเขียนข้อมูล

แถบนี้**คำนวณสดตอน render จากวันที่ของงานที่มีอยู่** ไม่เพิ่มฟิลด์ ไม่เรียก `piSaveTask` ไม่แก้ค่าใน `PIMPL` ไม่แตะ Firestore

ถ้าลบโค้ดส่วนนี้ออก ข้อมูลจะเหมือนเดิมทุกประการ

## เงื่อนไขที่ตรวจแล้วว่ารองรับ

**ระบบพิกัดตรงกันอยู่แล้ว** — `.g-deprow` เป็น `position:relative` และอยู่ใน `.g-body{min-width:max-content}` ซึ่งกว้างเท่าแถวงาน (250px + ความกว้างไทม์ไลน์) วางแถบแบบ absolute ที่ `left: 250 + วันเริ่ม × dw` จึงตรงกับแถบงานด้านล่างพอดี

เป็นเทคนิคเดียวกับเส้นวันนี้ที่ใช้ `left:${250+tx}px` อยู่แล้ว

**ข้อมูลช่วงวันคำนวณได้จากของที่มี** — `byp[ph]` คือรายการงานของเฟสหลังกรอง และ `piSpan(d)` คืนช่วงจริงของงาน (งานแม่คิดจากงานย่อย) ไม่ต้องเพิ่มฟิลด์ใหม่

`renderPhaseTimeline()` คำนวณ min/max ต่อเฟสแบบเดียวกันอยู่แล้ว ยืนยันว่าข้อมูลรองรับ

## การคำนวณช่วงเฟส

ไล่ทุกงานใน `byp[ph]` เอา `piSpan(d)` แล้วหาวันเริ่มที่เร็วที่สุดกับวันจบที่ช้าที่สุด

ใช้ `piSpan` แทนค่า `d.s`/`d.e` ตรงๆ เพราะงานแม่อาจมีวันที่ค้างไม่ตรงกับงานย่อย — `piSpan` คิดจากงานย่อยจริงเสมอ

**คิดจากรายการที่ผ่านตัวกรองแล้ว** แถบจึงไม่ขัดกับสิ่งที่เห็นบนจอเมื่อเปิดตัวกรอง

ถ้าเฟสไม่มีงาน หรือไม่มีงานไหนมีวันที่ใช้ได้ → ไม่วาดแถบ

## รูปแบบ

แถวหัวเฟสสูง 24px ส่วนแถวงานสูง 38px ถ้าทำแถบเต็มความสูงจะดูหนักกว่าแถบงานจริงทั้งที่เป็นแค่สรุป

จึงใช้**แถบบาง 6px มุมมน** จัดกึ่งกลางแนวตั้ง ใช้สีของเฟสเอง (`--pc` ที่ตั้งไว้บน `.g-deprow` อยู่แล้ว) แบบโปร่ง เพื่อให้อ่านเป็นชั้นสรุป ไม่ใช่งานอีกชิ้น

```
● 02_Solution Definition (BRD)  28   ━━━━━━━━━━━━━━━━━━━━
    ● BRD Company Structure          ▭▭▭▭▭▭▭▭
    ● BRD General Accounting              ▭▭▭▭▭▭▭▭
```

## จุดที่ต้องระวัง และทางแก้

**ป้ายชื่อเฟสเป็น `position:sticky;left:4px` z-index 4** — พอเลื่อนจอไปขวา ป้ายจะลอยทับต้นแถบ ปล่อยให้แถบลอดใต้ป้าย (แถบใช้ `z-index:1`) ซึ่งเป็นพฤติกรรมปกติของ Gantt ทั่วไป

**แถวหัวเฟสมี `onclick="piTogglePhase()"`** — แถบตั้ง `pointer-events:none` การกดตรงแถบจึงยังยุบ/กางเฟสได้เหมือนเดิม ไม่เปลี่ยนพฤติกรรมที่ผู้ใช้คุ้นอยู่

## ผลพลอยได้

ตอนยุบเฟส ปัจจุบันเหลือแค่ป้ายชื่อ ไม่เห็นไทม์ไลน์เลย พอมีแถบนี้ การยุบทุกเฟสจะกลายเป็นมุมมองสรุปที่เห็นภาพรวมทั้งโครงการในจอเดียว

## ไม่ทำ

- ไม่แสดงความคืบหน้าในแถบ — ขอบเขตที่ขอคือช่วงเวลา ถ้าต้องการค่อยเพิ่มทีหลัง
- ไม่แตะแถบงาน การลาก การซูม หรือ `renderGantt()` ของหน้า ROI
- ไม่เพิ่มฟิลด์ ไม่แตะชั้นบันทึกข้อมูล

## การตรวจสอบ

1. แถวหัวเฟสมีแถบ และตำแหน่งซ้าย/ความกว้างตรงกับขอบเขตของงานในเฟสนั้น
2. เฟสที่ไม่มีงาน หรืองานไม่มีวันที่ → ไม่มีแถบ ไม่มี error
3. เปิดตัวกรอง แถบหดตามรายการที่เหลือจริง
4. กดที่แถบยังยุบ/กางเฟสได้
5. ยุบทุกเฟสแล้วยังเห็นแถบครบทุกเฟส
6. **ไม่มีการเรียก `piSaveTask` / `DB.saveItem` จากโค้ดที่เพิ่ม** — ตรวจด้วยการอ่าน diff
7. `node --check` ผ่าน · ไม่มี JS error

## รอบที่ 2 — ใส่ชื่อเฟสลงในแถบ

**วันที่:** 2026-08-06 (ต่อจากรอบแรก)

ผู้ใช้เห็นผลจริงแล้วขอให้แถบแสดงชื่อ เหมือนแถบงานอย่าง `BRD Company Structure & General Setup`

### เงื่อนไขที่บังคับให้แถวต้องสูงขึ้น

แถบงาน `.g-bar` **สูง 28px** แต่แถวหัวเฟสสูงแค่ **24px** — เตี้ยกว่าตัวแถบที่จะใส่เข้าไป จึงต้องเพิ่มความสูงแถว ไม่มีทางเลี่ยง

ผู้ใช้เลือกแบบ**กระทัดกว่าแถบงาน**: แถว 30px · แถบ 22px · ชื่อ 11px — เล็กกว่าแถบงาน (28px/12px) อย่างชัดเจน ลำดับชั้นระหว่างเฟสกับงานจึงยังอ่านออกจากขนาด

### เรื่องชื่อซ้ำ — ตรวจแล้วว่าเป็นแพทเทิร์นเดิมของแอป

กังวลตอนแรกว่าชื่อเฟสในแถบจะซ้ำกับป้ายด้านซ้าย แต่**แถวงานทำแบบนี้อยู่แล้ว** — ชื่ออยู่ทั้งใน `.g-lab` และใน `.g-bname` การทำแบบเดียวกันกับเฟสจึงสอดคล้อง ไม่ใช่ของใหม่

### จำกัดขอบเขตความสูง

`.g-deprow` **ถูกใช้โดยหน้า ROI ด้วย** (`renderGantt`) การแก้กฎกลางจะทำให้แถวกลุ่มของหน้านั้นสูงตามทั้งที่ไม่มีแถบเฟส

จึงใส่ `height:30px` ไว้ในกฎที่จำกัดขอบเขตอยู่แล้ว (`#piGantt .g-deprow,#apGantt .g-deprow`) **กฎกลาง `.g-deprow{height:24px}` ไม่ถูกแตะ**

### แยกจากแถบงานด้วยสีของเฟส

ถ้าหน้าตาเหมือนแถบงานเป๊ะจะแยกไม่ออกว่าอันไหนเฟสอันไหนงาน จึงย้อมด้วย `--pc` (สีเฟสที่ตั้งบนแถวอยู่แล้ว) — พื้น 12% ขอบ 38% จุดและตัวอักษรเป็นสีเต็ม เข้าชุดกับป้ายชื่อเฟสด้านซ้ายที่ใช้สีเดียวกัน

### ชื่อยาวกว่าแถบ

`overflow:visible;white-space:nowrap` ชื่อล้นออกนอกแถบได้ เหมือนแถบงานสั้น ๆ ที่มีอยู่แล้ว และ `min-width` เป็น 6px เท่าแถบงาน

จำลองกับข้อมูล seed: `01_Planning & Kick-off` (แถบ 75px) และ `07_On-Going Support` (แถบ 20px) ชื่อจะล้นออกมา ส่วนอีก 5 เฟสชื่ออยู่ในแถบพอดี

### ไม่มีอะไรพังจากการเพิ่มความสูง

`drawPIDeps()` วาดเส้นเชื่อมงานจาก `getBoundingClientRect()` ทุกจุด จึงปรับตามความสูงใหม่เอง ไม่มีที่ไหนใน Gantt hardcode ความสูงแถว

### ยังไม่เขียนข้อมูลเหมือนเดิม

ตรวจ diff แล้ว 0 คำสั่งเขียน — ยังเป็นการอ่านและวาดล้วน

## รอบที่ 3 — ตั้งวันที่ของเฟสเองได้

**วันที่:** 2026-08-06

ผู้ใช้ระบุชัดว่าต้องการแค่ **ตั้งวันที่ของเฟสได้** และ **มีชื่อเฟสบนแถบ** เพื่อให้ตอนยุบหัว node ทุกอันแล้วเห็นภาพรวมทั้งโครงการ

รอบก่อนหน้าผมเสนอระบบเทียบแผนกับจริง (แถบสองชั้น + ตัวเลขส่วนต่าง) ซึ่ง**เกินความต้องการ** และถูกปฏิเสธ บันทึกไว้เพื่อไม่ให้เสนอซ้ำ

### โมเดล — ค่าที่ตั้งเองมาก่อน ไม่มีก็คำนวณ

เอกสารเฟสรับฟิลด์ `s` / `e` เพิ่ม (ไม่บังคับ)

```
ถ้าเฟสมี s และ e ที่แปลงเป็นวันที่ได้ทั้งคู่ → ใช้ค่านั้น
ไม่งั้น                                    → คำนวณจากงานเหมือนเดิม
```

**ไม่มี second source of truth** เพราะมีชุดวันเดียวต่อเฟสเสมอ ไม่ใช่สองชุดที่ต้องมาตัดสินว่าเชื่ออันไหน

เฟสที่ยังไม่ตั้งวันแสดงผลเหมือนเดิมทุกประการ **ไม่มีการเติมค่าอัตโนมัติ** ข้อมูลเดิมไม่ถูกแตะจนกว่าผู้ใช้จะตั้งเอง

### ทดสอบตรรกะครบทุกกรณี

| กรณี | ผลลัพธ์ |
|---|---|
| ไม่ตั้งวัน | คำนวณจากงาน |
| ตั้งครบสองวัน | ใช้ค่าที่ตั้ง |
| ตั้งแค่วันเริ่ม | ถอยไปคำนวณจากงาน |
| ตั้งแค่วันจบ | ถอยไปคำนวณจากงาน |
| รูปแบบวันผิด | ถอยไปคำนวณจากงาน |
| ล้างค่า | ถอยไปคำนวณจากงาน |

### การแก้ไข

ปุ่มปฏิทินเพิ่มใน `.g-phacts` ข้างปุ่มเปลี่ยนชื่อ กดแล้วชื่อเฟสกลายเป็นช่องกรอกวันสองช่อง `dd/mm/yyyy → dd/mm/yyyy`

ตามแพทเทิร์นเดียวกับ `piRenameInline` ทุกประการ — Enter บันทึก · Escape ยกเลิก · คลิกออกบันทึก · `stopPropagation` กันไม่ให้ไปยุบเฟส

**ล้างช่องให้ว่างแล้วกด Enter = กลับไปคำนวณจากงานอัตโนมัติ** เป็นทางถอยที่ชัดเจน

ไม่ทำแบบลากแถบเพราะ Playwright ยังหลุด ทดสอบ interaction จริงไม่ได้

### ไม่แตะข้อมูลงาน

การบันทึกเรียก `piPhSave` อย่างเดียว ซึ่งเขียนลง `COL_PH` (`pi_phases` / `ap_groups`) **คนละคอลเลกชันกับงาน** (`pi_tasks` / `ap_tasks`)

ตรวจ diff แล้ว: ไม่มี `piSaveTask` ไม่มีการแก้ฟิลด์ของงาน ไม่แตะ `PIMPL`

## รอบที่ 4 — แก้สีชนกัน เปลี่ยนเป็นวงเล็บคร่อม

**วันที่:** 2026-08-06

ผู้ใช้ขอให้วิเคราะห์ผลจริงในฐานะนักออกแบบ พบปัญหาที่วัดได้ และ**เกิดจากรอบที่ 2 ของเอกสารนี้เอง**

### สีเฟสชนกับสีสถานะครบทุกคู่

| เฟส | สี | ชนกับสถานะ | ห่างกัน |
|---|---|---|---|
| 01 | `#28cd41` | Completed `#28cd41` | **0°** |
| 03 | `#ff9500` | In Progress `#ff9500` | **0°** |
| 04 | `#af52de` | On Hold `#af52de` | **0°** |
| 07 | `#8e8e93` | Not Started `#8e8e93` | **0°** |
| 02 | `#0a7cff` | In Review `#0071e3` | 2° |
| 06 | `#5ac8fa` | In Review | 11° |
| 05 | `#ff2d55` | Delayed `#ff3b30` | 15° |

**4 เฟสเป็นสีเดียวกันเป๊ะกับสถานะ**

การชนนี้**ไม่เคยเป็นปัญหามาก่อน** เพราะสีเฟสอยู่แต่ในคอลัมน์ซ้าย ส่วนสีสถานะอยู่แต่ในไทม์ไลน์ — แยกกันด้วยเขตพื้นที่ การเอาสีเฟสไปวาดในไทม์ไลน์คือสิ่งที่พังกำแพงนั้น

เป็นปัญหาชนิดเดียวกับผัง Oracle ใน `2026-08-05-oracle-lane-colors-design.md` — ระบบสีสองชุดแย่งช่องทางเดียวกัน

### ปัญหาอื่นที่พบพร้อมกัน

**รูปทรงบอกว่าเป็นงาน** — การ์ดมุมมนมีจุด+ชื่อ คือไวยากรณ์เดียวกับแถบงาน ทั้งที่ Gantt มาตรฐานใช้วงเล็บคร่อมสำหรับ summary โดยเฉพาะ และแอปนี้มีธรรมเนียมอยู่แล้ว (`.pi-sum{border:1px dashed}`)

**ชื่อซ้ำโดยไม่จำเป็น** — ป้ายซ้ายเป็น `position:sticky` ไม่มีวันเลื่อนหาย ชื่อเฟสจึงเห็นตลอด เหตุผลเดิมที่ว่า "แถบงานก็ทำ" ใช้ไม่ได้ เพราะชื่องานในคอลัมน์ซ้ายถูกตัดด้วย ellipsis แต่ชื่อเฟสแสดงเต็ม

### สิ่งที่แก้

```
ก่อน   ┌────────────────────────┐   การ์ดสีเฟส
       │ ● 02_Solution Definition │
       └────────────────────────┘

หลัง   02_Solution Definition
       ⌐──────────────────────¬     วงเล็บสีกลาง
```

วงเล็บทำด้วย `border` บน+ซ้าย+ขวา ตัด `border-bottom` ออก ได้ทรง ⊓ ที่เป็นสัญลักษณ์สากลของ summary

**หลักการที่ได้กลับคืน: คอลัมน์ซ้าย = ตัวตน (สีเฟส) · ไทม์ไลน์ = สถานะ (สีสถานะ)** แยกด้วยเขตพื้นที่ ไม่ต้องแก้จานสีเลย

ตรวจแล้ว `--pc` เหลือใช้เฉพาะ `.g-dept` `.g-dn` `.g-phname` ซึ่งอยู่ในคอลัมน์ซ้ายทั้งหมด

### เลือกสีกลางจาก contrast จริง

| ตัวแปร | light | dark | ใช้กับ |
|---|---|---|---|
| `--ink3` | **2.57** | 4.27 | จางเกินไป ไม่ใช้ |
| `--ink2` | 4.52 | 6.30 | **วงเล็บ** |
| `--ink` | 16.83 | 12.80 | **ป้ายชื่อ** — เป็นหัวข้อที่ต้องกวาดอ่านตอนยุบ |

`Not Started` เป็นสีเทาเหมือนกัน แต่เป็นจุด/ป้ายทึบ ต่างจากวงเล็บที่เป็นเส้นขอบเปล่า และเทาในที่นี้คือสีกลางของ UI ไม่ใช่สีที่ถือความหมาย

### เรขาคณิตในแถว 30px

วงเล็บ y 18–26 · ป้ายชื่อ y 1–16 — อยู่ในแถวพอดีทั้งคู่ ไม่ล้น

| สถานะแถว | แสดงเป็น | เหตุผล |

| **กาง** | วงเล็บคร่อม | งานข้างล่างบอกรายละเอียดอยู่แล้ว เฟสเป็นแค่ตัวคุมขอบเขต |
| **หุบ** | แถบเต็มแบบแถบงาน | แถบเฟสคือสิ่งเดียวที่แทนงานทั้งเฟส ต้องแบกข้อมูลเอง |

### สีของแถบตอนหุบ — รวมสถานะ ไม่ใช่สีเฟส

ถ้าใช้สีเฟสจะกลับไปชนกับสีสถานะที่เพิ่งแก้ในรอบที่ 4 เพราะเมื่อบางเฟสหุบและบางเฟสกาง จะมีแถบสีเฟสกับแถบสีสถานะอยู่บนจอพร้อมกัน

จึงใช้ `piPhRoll(list)` **รวมสถานะจากงานในเฟส** ด้วยกติกาเดียวกับ `piRollStatus` ของงานแม่

```
ทุกงาน Completed              → Completed
ทุกงาน Not Started            → Not Started
มี Delayed แม้ตัวเดียว        → Delayed
มี On Hold แม้ตัวเดียว        → On Hold
ทุกงานเป็น In Review/Completed → In Review
นอกนั้น                       → In Progress
```

**สีจึงยังหมายถึงสถานะเสมอ** หลักการจากรอบที่ 4 ไม่ถูกทำลาย และได้ข้อมูลเพิ่มฟรี — เห็นทันทีว่าเฟสไหนเสร็จแล้ว เฟสไหนยังไม่เริ่ม

ผลกับข้อมูล seed: `01_Planning` = Completed (เขียว) · `02_Solution Definition` = In Progress (ส้ม) · ที่เหลือ = Not Started (เทา)

### องค์ประกอบของแถบตอนหุบ

จุดสี + ชื่อเฟส + ป้ายสถานะรวม — เหมือนแถบงานอย่าง `BRD Company Structure & General Setup` ตามที่ผู้ใช้ระบุ

สูง 24px เตี้ยกว่าแถบงาน 28px เล็กน้อย เพื่อคงลำดับชั้นและให้แถวกระชับตอนหุบทุกเฟส ซึ่งเป็นตอนที่อยากเห็นเฟสเยอะ ๆ พร้อมกัน

### การทับค่า CSS

`.g-phbar.col` (specificity 0,2,0) ทับ `.g-phbar` (0,1,0) ครบทุกค่าที่ขัดกัน

| | วงเล็บ | แถบเต็ม |
|---|---|---|
| `bottom` | `4px` | `auto` |
| `height` | `8px` | `24px` |
| `border` | `2px solid var(--ink2)` ตัดล่าง | `1px solid var(--line)` ครบสี่ด้าน |
| `border-radius` | `3px 3px 0 0` | `8px` |
| `background` | `none` | inline ตามสถานะ |

`.g-phbar.col .g-phlab` เปลี่ยนป้ายจาก absolute (ลอยเหนือวงเล็บ) เป็น static (อยู่ในแถบ) และขยายเป็น 12px

### ยังไม่เขียนข้อมูล

`piPhRoll` เป็นการอ่านล้วน ไม่บันทึกสถานะที่รวมได้ลงที่ไหน — ต่างจาก `piRollStatus` ที่เขียนกลับลงงานแม่ ตรวจ diff แล้วไม่มีคำสั่งเขียน
