# บันทึกและแสดงการเลื่อนกำหนดส่ง

**วันที่:** 2026-09-09
**ขอบเขต:** `index.html` — งานใน Gantt แผนงานโครงการ (`PIMPL` / `GCTX==='pi'`)

## ที่มา

งานบางตัวถูกเลื่อนกำหนดหลายรอบ ต้องรู้ว่า**เลื่อนกี่ครั้ง เลื่อนจากวันไหนไปวันไหน และทำไม**
โดยเห็นได้ทั้งในหน้ารายละเอียดและกวาดตาจากแถบ Gantt

`due` ของงานในผังนี้คือ **วันสิ้นสุด `d.e`**

## โมเดล

```js
d.dueLog = [
  { from:'12/05/2026', to:'20/05/2026', at:'07/08/2026 10:20', why:'รอ PS Global ส่ง BRD กลับ' },
  { from:'20/05/2026', to:'27/05/2026', at:'08/08/2026 11:21', why:'ปรับตามมติที่ประชุม' }
]
```

`from`/`to` เป็น `วว/ดด/ปปปป` ตามทั้งแอป · `at` ใช้ `piLogStamp()` ตัวเดียวกับบันทึกความคืบหน้า

`piSaveTask(d)` บันทึกทั้งอ็อบเจกต์โดยไม่มี allow-list ฟิลด์ใหม่จึงลง Firestore เอง
**ไม่ต้องแก้ชั้น persistence** — แบบเดียวกับ `rvw` ใน PR #47

### ตัวเลขสรุปต้องโกหกไม่ได้

| ค่า | คำนวณจาก |
|---|---|
| กำหนดเดิม | `dueLog[0].from` |
| เลื่อนกี่ครั้ง | `dueLog.length` |
| รวมกี่วัน | **`d.e` ปัจจุบัน − กำหนดเดิม** |

รวมกี่วัน **ไม่ได้บวกจาก log** แต่คิดจากวันปัจจุบันจริง เพราะ `d.e` ยังเปลี่ยนได้อีก 2 ทาง
คือลากแถบใน Gantt กับแก้ช่องวันสิ้นสุด ซึ่งไม่ผ่านปุ่ม — ถ้าบวกจาก log ตัวเลขจะเพี้ยนทันทีที่มีคนลาก

และถ้า `d.e` ไม่ตรงกับปลายทางของรายการล่าสุด `piDueInfo()` จะคืน `drift` ออกมา
หน้ารายละเอียดขึ้นบรรทัดเตือนว่า *"มีการแก้กำหนดหลังจากนี้โดยไม่ได้บันทึกเหตุผล (27/05 → 01/06)"*

**เจตนาคือทำให้ช่องโหว่มองเห็นได้ แทนที่จะปิดทางแก้วันที่** — ต้องแก้วันพิมพ์ผิดได้ ต้องลากปรับได้
สิ่งที่ทำไม่ได้คือปล่อยให้ข้อมูลดูน่าเชื่อถือทั้งที่ไม่ครบ

## ปุ่มเลื่อนกำหนด

อยู่ใต้แถววันเริ่ม/วันสิ้นสุดในหน้ารายละเอียด คู่กับบรรทัดสรุป

```
วันเริ่ม [04/05/2026]   วันสิ้นสุด [29/05/2026]
[ เลื่อนกำหนด ]  เดิม 12/05/2026 · เลื่อน 2 ครั้ง · +17 วัน
```

กดแล้วกางฟอร์ม: วันกำหนดใหม่ (เติมค่าปัจจุบันไว้ให้) + เหตุผล + ยกเลิก/บันทึก

`piDueSave()` ทำตามลำดับ: ตรวจรูปแบบวันที่ → กันวันซ้ำเดิม → `push` เข้า `dueLog` → ตั้ง `d.e`
→ `piSaveTask()` **ครั้งเดียว** → `piEnforce()` ให้งานที่ผูก dependency ขยับตาม → `renderPI()` → `renderProjRibbon()`

เหตุผลปล่อยว่างได้ (บางครั้งยังไม่รู้) แต่ประวัติจะขึ้นว่า *— ไม่ได้ระบุเหตุผล —* ให้เห็นชัด

## ประวัติในหน้ารายละเอียด

ใช้คลาส `.lgi` / `.lgt` / `.lgm` ชุดเดียวกับบันทึกความคืบหน้า จะได้เป็นของระบบเดียวกัน
วางไว้**เหนือ**บันทึกความคืบหน้าในคอลัมน์ขวา

```
ประวัติการเลื่อนกำหนด (2)
① 12/05/2026 → 22/05/2026  +10 วัน          07/08/2026 10:20  ×
  รอ PS Global ส่ง BRD กลับ
② 22/05/2026 → 29/05/2026  +7 วัน           08/08/2026 11:21  ×
  ปรับตามมติที่ประชุม 22/08
```

**เรียงเก่า→ใหม่ ต่างจากบันทึกความคืบหน้าที่เรียงใหม่ก่อน** — เพราะ "เลื่อนครั้งที่ 1 2 3"
อ่านเป็นลำดับเวลา ถ้ากลับหัวเลขจะไล่ถอยหลังแล้วงง

**แก้เหตุผลได้ (คลิกที่ข้อความ) · ลบรายการได้ · แก้วันที่ในประวัติไม่ได้** — วันที่กับเวลาคือหลักฐาน
ส่วนเหตุผลคือคำอธิบายที่ควรแก้คำผิดได้ การลบถามยืนยันและบอกด้วยว่าวันกำหนดปัจจุบันไม่เปลี่ยน

## บนแถบ Gantt

```
                       ╷ กำหนดเดิม
   ╭───────────────────┊────╮
   │ ● Planning and Kick Off │  ● Completed   ↻2
   ╰───────────────────┊────╯
```

- **เส้นประตั้ง + หัวจุด** ที่ `left = (dayOf(กำหนดเดิม)+1) × dw` ซึ่งคือขอบขวาที่แถบ *เคย* จบ
  (แถบกว้าง `(b−a+1)×dw` ขอบขวาจึงอยู่ที่ `(b+1)×dw` — สูตรเดียวกัน เลื่อน/ซูมตามกันเอง)
- **ชิปนับครั้ง** `↻n` ต่อจากชิปสถานะ เฉพาะแถบใหญ่ · แถบบาง (งานย่อย) ไม่มีที่ใส่ จึงมีแต่เส้น
- `title` ของทั้งแถวเติม `· กำหนดเดิม X · เลื่อน n ครั้ง · +m วัน` — ครอบคลุมแถบบางที่ไม่มีชิป

**สีทั้งหมดเป็น `--ink3` เทา** ไม่ใช้สีใหม่ เพราะสีในแอปนี้จองไว้ให้สถานะอย่างเดียว (PR #44/#54/#62)
เส้นเป็น `pointer-events:none` จึงไม่ขวางการลากแถบ

แยกจากเส้นตารางได้เพราะเส้นตารางเป็น **เส้นทึบ** สี `--line2` (จางมาก) ส่วนตัวนี้ **เส้นประ**
สี `--ink3` และมีหัวจุด

## รวมยอดที่หัวเฟส

```
02_Solution Definition (BRD)  13   ↻ 3 งาน · รวม 35 วัน
```

นับทุกงานในเฟสที่มี `dueLog` และบวกจำนวนวันที่เลื่อนของแต่ละงาน
เฟสที่ไม่มีงานถูกเลื่อนจะไม่มีชิปเลย และชิปยังเห็นตอนยุบเฟส — ซึ่งเป็นตอนที่ต้องการมันที่สุด
เพราะมองไม่เห็นงานข้างใน

**ชิปเป็นเทาบนพื้นขาว ไม่รับสี `--pc` ของเฟส** ทั้งที่อยู่ในกล่องที่ย้อมสีสถานะเฟสอยู่ —
เพราะสีในแอปนี้แปลว่าสถานะ ถ้าชิปการเลื่อนกลายเป็นสีเขียวตามเฟสที่เสร็จแล้วจะอ่านผิดทันที

**ข้อจำกัดที่ต้องรู้:** ถ้างานแม่และงานลูกถูกเลื่อนทั้งคู่ จะนับสองครั้งและบวกวันซ้ำ
ตัวเลขนี้จึงอ่านว่า *"รวมวันที่ถูกเลื่อนของทุกงานในเฟส"* ไม่ใช่ *"เฟสนี้จบช้ากว่าแผนกี่วัน"*
ซึ่งเป็นคนละคำถามและต้องมี baseline ระดับเฟสถึงจะตอบได้

## ไม่ทำ

- ไม่แตะ Action Items และ Automation Gantt (`GCTX==='ap'` คืน `_di=null`) —
  แต่ `renderPIGantt` ใช้ร่วมกัน ถ้าจะเปิดให้ Automation ทีหลังแค่ถอดเงื่อนไขออก
- ไม่เพิ่มตัวกรอง "เฉพาะงานที่ถูกเลื่อน" หรือ KPI นับจำนวนงานที่เลื่อน — รอมีข้อมูลจริงก่อน
- ไม่บังคับให้ทุกการเปลี่ยนวันสิ้นสุดต้องผ่านปุ่ม — ดูหัวข้อ drift ข้างบน
- ไม่ย้ายข้อมูลเดิม — งานที่ไม่มี `dueLog` ไม่แสดงอะไรเพิ่มเลย

## การตรวจสอบ

1. งานที่ยังไม่เคยเลื่อน: มีปุ่ม · ฟอร์มยังไม่กาง · ไม่มีบรรทัดสรุป · ไม่มีประวัติ
2. กดปุ่ม → ฟอร์มกาง ปุ่มซ่อน ช่องวันเติมค่าปัจจุบันไว้
3. เลื่อน 2 ครั้ง → `dueLog` มี 2 รายการถูกต้อง · `d.e` เป็นวันล่าสุด ·
   สรุปอ่านว่า `เดิม 12/05/2026 · เลื่อน 2 ครั้ง · +15 วัน` · ประวัติเรียง 1,2
4. บน Gantt: **ระยะจากเส้นประถึงขอบขวาแถบ = จำนวนวันที่เลื่อน × dw** (วัดจริง 75px = 15 วัน × 5)
5. ชิปแสดงเลขถูกและอยู่ในแถบ · `pointer-events` ของเส้นเป็น `none` · `title` แถวมีข้อมูลครบ
6. แก้ `d.e` ตรงๆ (จำลองการลากแถบ) → ขึ้นเตือน drift และตัวเลขรวมอัปเดตตามความจริง
7. ไม่มี JS error · regression ชุด PR #46–#62 ผ่านครบ · การนำทาง PR #63 ปกติ
8. หัวเฟส: เลื่อน 3 งาน +12/+15/+8 → ชิปอ่านว่า `3 งาน · รวม 35 วัน` · เฟสที่ไม่มีการเลื่อนไม่มีชิป (1 ใน 7) · ยุบเฟสแล้วยังเห็น
9. ทุกรอบทดสอบ stub `DB.saveItem`/`deleteItem` ไว้ก่อน — ไม่มีการเขียนข้อมูลจริง
