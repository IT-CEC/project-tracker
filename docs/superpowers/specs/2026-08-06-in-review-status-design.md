# สถานะ In Review + ฝั่งที่กำลังตรวจ (Civil / PS Global)

**วันที่:** 2026-08-06
**ขอบเขต:** `index.html` — ชุดสถานะร่วม + ฟิลด์ฝั่งผู้ตรวจของ task ใน Overall Project Plan

## ที่มา

ต้องการสถานะ `In Review` เพิ่มจากเดิม 5 สถานะ และการตรวจมีสองฝั่งคือ Civil กับ PS Global

**ความหมายที่ผู้ใช้ยืนยัน:** งานไปทีละฝั่ง — งานหนึ่งอยู่ที่ฝั่งเดียวในเวลาหนึ่ง ส่ง Civil ก่อน พอเสร็จจึงส่งต่อ PS Global จึงต้องรู้ว่า *ตอนนี้ค้างอยู่ที่ใคร*

นี่ต่างจากหน้า Tracking (Action Items) ที่ทั้งสองฝั่งทำงานคู่ขนานและมีสถานะของตัวเองแยกกัน (`status` + `status2`) จึงไม่ยกโมเดลนั้นมาใช้ซ้ำ

## โมเดล

สถานะยังเป็น**ชุดเดียว** เพิ่มค่าใหม่ และเพิ่มฟิลด์บอกฝั่ง

```
st  : 'In Review'              ← ค่าใหม่ใน STATUS_LIST
rvw : 'Civil' | 'PS Global'    ← ฟิลด์ใหม่ มีความหมายเฉพาะตอน st === 'In Review'
```

ตั้งต้นเป็น `Civil` เมื่อเปลี่ยนสถานะมาเป็น In Review เพราะเป็นฝั่งแรกของลำดับ

`piSaveTask()` บันทึกทั้งอ็อบเจกต์โดยไม่มี allow-list ฟิลด์ `rvw` จึงลง Firestore เองอัตโนมัติ **ไม่ต้องแก้ชั้น persistence**

## ตำแหน่งในลำดับสถานะ

```
Not Started → In Progress → In Review → On Hold → Delayed → Completed
                              ↑ แทรกใหม่
```

วางต่อจาก In Progress ให้อ่านเป็นสายงาน โดย On Hold / Delayed ยังเป็นสถานะข้อยกเว้นอยู่ท้ายตามเดิม

## Progress

`piCalcProg` เพิ่ม `'In Review': 75`

| สถานะ | % |
|---|---|
| Not Started | 0 |
| In Progress · On Hold · Delayed | 50 |
| **In Review** | **75** |
| Completed | 100 |

งานที่เข้ารีวิวคือทำเสร็จแล้วรออนุมัติ จึงคืบหน้ากว่า In Progress **ผลข้างเคียงที่ตั้งใจ: KPI "Actual %" บนแดชบอร์ดจะขยับขึ้นเมื่องานเข้ารีวิว**

## บอร์ด Status — 1 คอลัมน์ ไม่ใช่ 2

`.kcol` กว้างตายตัว 282px และ `.kb` เลื่อนแนวนอน ปัจจุบัน 5 คอลัมน์ = 1,466px ซึ่งเต็มจอ 1440px พอดีอยู่แล้ว

| ทางเลือก | ความกว้างรวม |
|---|---|
| In Review 1 คอลัมน์ (รวม 6) | ~1,762px |
| แยก Civil / PS Global (รวม 7) | ~2,058px |

เลือก 1 คอลัมน์ แล้วให้**หัวคอลัมน์บอกคิวของแต่ละฝั่ง** ได้ข้อมูลเท่าการแยกคอลัมน์โดยไม่ต้องเลื่อนจอเพิ่ม — เป็นแพทเทิร์นเดียวกับการ์ด KPI ของ Action Items ที่แสดง `Civil | PS Global` เป็นคู่อยู่แล้ว

```
● In Review  5
  Civil 3 · PS 2

┌────────────────────────┐
│ BRD General Accounting │
│ [02_Solution] [Civil]  │  ← badge บอกฝั่ง
│ ◐ 75%   17/06 → 20/07  │
└────────────────────────┘
```

`renderPIKb()` เป็นฟังก์ชันร่วมของบอร์ด Status และ Priority จึงเพิ่มเป็น**พารามิเตอร์เสริม** สำหรับ sub-label ใต้หัวคอลัมน์ ไม่ผูกตรรกะ In Review ลงไปในตัวฟังก์ชัน บอร์ด Priority ที่ไม่ส่งพารามิเตอร์นี้จึงไม่เปลี่ยนพฤติกรรม

## จุดที่แสดงฝั่ง

| ที่ | แสดงอย่างไร |
|---|---|
| การ์ดบนบอร์ด Status | badge `Civil` / `PS Global` ต่อจาก chip เฟส |
| แถบใน Gantt | pill `In Review` แล้วตามด้วย chip ฝั่งแยกอีกอัน |
| หน้าต่างแก้ไขงาน | ดรอปดาวน์ที่สอง โผล่เฉพาะตอนสถานะเป็น In Review |
| หัวคอลัมน์ In Review | `Civil n · PS n` |

pill ใน Gantt **ไม่รวมชื่อฝั่งไว้ในข้อความเดียวกัน** เพราะ `In Review · PS Global` ยาวกว่าสถานะอื่นมากและ pill อยู่ติดกับแถบงานที่อาจแคบ แยกเป็น chip ต่างหากจึงตัดบรรทัดได้เองโดยไม่ดันแถบ

## หน้าอื่นที่ได้รับผล

`STATUS_LIST` ใช้ร่วมกัน 3 หน้า ผู้ใช้เลือกให้ In Review ขึ้นทั้งหมด

| หน้า | ได้อะไร |
|---|---|
| Overall Project Plan (PI + AP) | สถานะ In Review **+ ฟิลด์ฝั่ง** |
| Requirements | สถานะ In Review เฉยๆ ไม่มีฝั่ง |
| Bridge | สถานะ In Review เฉยๆ ไม่มีฝั่ง |

ฟิลด์ฝั่งอยู่เฉพาะ task ของ Overall Project Plan ตามที่ผู้ใช้ระบุบริบทมา ถ้าภายหลังต้องการที่ Requirements/Bridge ด้วยค่อยเพิ่ม

## ไม่ทำ

- ไม่แตะโมเดลสองสถานะของ Action Items (`status` / `status2`) — คนละความหมาย
- ไม่เพิ่มตัวกรองแยกฝั่ง — หัวคอลัมน์บอกจำนวนแล้ว ถ้าต้องการค่อยเพิ่มทีหลัง
- ไม่ย้ายข้อมูลเดิม — งานที่มีอยู่ไม่มีใครเป็น In Review จึงไม่ต้อง migrate

## การตรวจสอบ

1. บอร์ด Status มี 6 คอลัมน์ In Review อยู่ต่อจาก In Progress และหัวคอลัมน์แสดง `Civil n · PS n` ถูกต้องตามจำนวนจริง
2. บอร์ด Priority ยังเหมือนเดิมทุกประการ (ไม่ได้รับ sub-label)
3. ตั้งงานเป็น In Review → เลือกฝั่งได้ → badge ขึ้นบนการ์ดและ chip ขึ้นใน Gantt
4. เปลี่ยนสถานะออกจาก In Review → ดรอปดาวน์ฝั่งหายไป
5. progress ของงาน In Review = 75% และ KPI ระดับเฟสคำนวณตาม
6. ดรอปดาวน์กรองสถานะทั้ง 3 หน้ามี In Review และกรองได้จริง
7. `rvw` บันทึกลง Firestore แล้วอ่านกลับมาได้ (ทดสอบโดย stub `DB.saveItem` ตรวจ payload)
8. Requirements และ Bridge เลือก In Review ได้ ไม่มีดรอปดาวน์ฝั่งโผล่มา
9. ไม่มี JS error · ทุก panel ยัง render ปกติทั้ง light/dark
